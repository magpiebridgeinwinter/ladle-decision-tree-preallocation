# 经统一约束校验的 Codex 兜底方案解决决策树贪心配包失败

## 摘要

规则驱动的决策树具有响应快、过程可追溯等特点，适合作为钢包预配的主路径，但局部贪心选择可能在生产扰动后占用稀缺资源，使后续约束更严格的炉次无法完成配包。本研究验证了一条分级响应路径：系统首先执行决策树；仅当决策树失败且仍有安全时间预算时，才采用 Codex 生成的兜底方案；任何 Codex 输出均须通过与决策树相同的硬约束终检。在一个包含两个受影响炉次的确定性模拟场景中，基线行车在最早开浇前 500 s 离线，扣除 90 s 安全缓冲后剩余 410 s。决策树仅完成 1/2 个炉次，准时率为 0.50。Codex 从两个炉次的整体资源关系出发，将近端行车保留给运输窗口仅为 10 s 的炉次，并将宽松炉次分配给另一台行车，最终完成 2/2 个炉次，准时率提高至 1.00，且未记录硬约束违反。本次结果证明了控制器能够接收、校验并采用当前 Codex 会话给出的兜底映射，但尚不能证明生产环境中的 Codex API 可用性、模型推理时延、跨场景稳定性或真实产线收益。

## 1. 引言

钢包预配需要在行车、钢包、设施或计划发生扰动时快速调整，同时不能放宽等级、载重、运行区间、时间窗和安全距离等生产约束。决策树能够显式过滤不可行资源，并对剩余候选进行规则评分，因此适合作为可解释、低时延的首选分配方法。当各炉次之间的资源依赖较弱时，这种逐炉次决策通常能够得到有效结果。

局部决策的局限在于，它只判断当前炉次的最优候选，未必会为后续炉次保留稀缺资源。如果一个时间窗宽松的炉次先占用了唯一能够满足紧急炉次的近端行车，即使系统仍存在完整的全局分配，后续炉次也可能被判定为无可行候选。因此，LLM 兜底的价值不应建立在放宽约束上，而应体现在决策树失败后识别跨炉次的资源依赖，并提出仍能通过确定性校验的全局映射。

本次演练验证现有分级响应控制器是否具备这一闭环能力。研究问题被限定为：当前 Codex 会话生成的完整配包映射，能否在决策树失败后进入现有 LLM 接口，比决策树多救回炉次，并在不绕过任何既有硬约束的情况下被控制器采用。

## 2. 方法

### 2.1 分级响应规则

对于发生时刻为 \(t_e\) 的扰动，系统根据受影响炉次的最早开浇时刻计算 LLM 可用预算：

\[
B=t_{\mathrm{pour,min}}-t_e-90\ \mathrm{s}。
\]

决策树始终首先执行。只有当决策树未能完成全部受影响炉次，且 \(B>0\) 时，控制器才允许调用 LLM 兼容接口。LLM 返回结果必须为每个受影响炉次提供唯一的 `heat_id`、`ladle_id` 和 `crane_id` 映射。控制器随后调用统一的 `validate_output` 终检；缺失炉次、重复炉次、未知资源或违反硬约束的方案均不能成为有效分配。

### 2.2 模拟扰动场景

场景包含两个受影响炉次、两个可用钢包和两台剩余行车。原基线行车 `C0` 在 \(t_e=100\) s 突发离线，两个炉次的开浇时刻均为 600 s，因此扣除 90 s 安全缓冲后，LLM 可用预算为 410 s。

`H-FLEX` 的优先级为 2，要求钢包等级为 4，运输时间窗为 1,000 s；`H-TIGHT` 的优先级为 1，强制要求等级 5，运输时间窗仅为 10 s。钢包 `L-FAR` 为等级 4，位于 100 m；钢包 `L-NEAR` 为等级 5，位于 0 m。行车 `C1` 初始位于 0 m，运行范围为 0–100 m；行车 `C2` 初始位于 100 m，已有载荷 150 t，运行范围为 50–150 m。两个钢包的重量均为 80 t，两台行车的最大载荷均为 300 t。

### 2.3 决策树基线

决策树按优先级首先处理 `H-FLEX`，评分后选择 `L-FAR/C1`，并把 `C1` 的工作位置更新到 100 m。处理 `H-TIGHT` 时，等级约束排除了 `L-FAR`；`C2` 的运行范围不能覆盖位于 0 m 的 `L-NEAR`；而 `C1` 从 100 m 返回 `L-NEAR` 又无法满足 10 s 时间窗。因此，决策树只能返回一个有效分配，另一个炉次保持未分配。

### 2.4 Codex 兜底方案

当前 Codex 会话接收了完整场景状态和决策树失败信息，并把两个炉次视为一个联合资源分配问题。Codex 给出的映射如下：

| 炉次 | 钢包 | 行车 | 决策理由 |
| --- | --- | --- | --- |
| `H-FLEX` | `L-FAR` | `C2` | 使用已经位于远端钢包位置的行车，把 `C1` 保留给紧时间窗炉次。 |
| `H-TIGHT` | `L-NEAR` | `C1` | 使用近端行车满足 10 s 运输时间窗。 |

该方案通过控制器的 LLM callable 接口注入。此次演练没有调用外部 Codex 或 OpenAI API，但控制器真实执行了兜底接口调用、方案完整性检查、硬约束终检、结果合并和指标计算。

### 2.5 约束校验与评价指标

统一校验器检查钢包等级、钢包状态、空包重量、行车载重、运行区间、到达时间窗和安全距离。在 Codex 方案中，`C2` 承运 `L-FAR` 后总载荷为 230 t，低于 300 t 上限；`C1` 承运 `L-NEAR` 后载荷为 80 t。两台行车均位于对应钢包的初始位置，因此在本场景坐标系中的预计到达时间均为 0 s。

主要评价指标为成功分配炉次数。次要指标包括准时率、优先级加权准时率、平均延迟、最大延迟和硬约束违反次数。所有路径采用同一指标函数计算。

## 3. 结果

Frozen 基线没有重新分配任何受影响炉次。决策树完成了 `H-FLEX`，但未能完成 `H-TIGHT`，因此只分配 1/2 个炉次，准时率为 0.50，优先级加权准时率为 0.67。由于决策树失败且剩余预算大于零，控制器随后进入 Codex 兜底路径。

Codex 返回的映射覆盖两个受影响炉次，且每个炉次只出现一次。统一校验器对两条记录均返回 `assign`，控制器最终进入 `llm_react_success`。与决策树相比，Codex 多救回 1 个炉次，使总体准时率和优先级加权准时率均达到 1.00，两条分配均未记录硬约束违反。

| 响应路径 | 成功分配 | 准时率 | 优先级加权准时率 | 平均延迟（s） | 最大延迟（s） | 硬约束违反 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Frozen | 0/2 | 0.00 | 0.00 | 505.0 | 1,000.0 | 0 |
| 决策树 | 1/2 | 0.50 | 0.67 | 5.0 | 10.0 | 0 |
| Codex 兜底 | 2/2 | 1.00 | 1.00 | 0.0 | 0.0 | 0 |

Frozen 和决策树失败记录中的“硬约束违反为 0”不代表分配成功。按照当前指标定义，未分配炉次会产生延迟，但不会被计为一条已经执行且违反约束的分配。因此，硬约束违反数必须与成功分配数及最终校验动作共同解读。

## 4. 讨论

该反例说明，LLM 兜底可以在不放宽约束的前提下补充局部贪心决策。决策树逐炉次优化，把近端行车分给了时间窗宽松的 `H-FLEX`；Codex 则识别出资源依赖的不对称性：`H-TIGHT` 只有 `L-NEAR/C1` 这一组可行的近端资源，而 `H-FLEX` 仍可由 `L-FAR/C2` 完成。通过为紧约束炉次保留稀缺资源，Codex 恢复了完整分配。收益来自跨炉次的联合推理，而不是降低安全标准。

本次结果同时验证了一项关键软件契约。控制器没有直接信任 Codex 声明的成功状态，而是先检查方案是否完整，再通过统一校验器重新判断每一条分配。只有完整映射和全部硬约束同时通过后，控制器才返回 `llm_react_success`。因此，Codex 在该架构中只负责提出候选方案，最终执行权仍由确定性规则控制。

本研究的证据范围有限。第一，场景是为暴露贪心失败而构造的合成反例，不能据此估计真实产线中此类失败的发生频率。第二，本次只运行了一个确定性扰动，没有重复试验、替代模型、全局优化器基线或消融实验。第三，Codex 方案由当前交互会话生成，再通过适配器注入；控制器记录的执行时间不包含模型推理、网络传输、重试和服务可用性，因此不能作为 Codex 时延。第四，现有校验器只能证明方案满足当前已经实现的逐项约束，不能代替对生产调度中全部时序交互的安全验证。

后续生产验证应从真实扰动日志中提取决策树失败样本，通过同一接口调用版本固定的 Codex 服务，并在脱敏审计中保留完整请求、响应和校验过程。同时，应在相同约束下加入确定性全局优化器作为对照，重复测量兜底成功率、时延分布、无效输出率、Frozen 避免率和人工复核需求。只有获得这些证据后，才能评价 Codex 兜底在真实生产中的稳定性和业务收益。

## 5. 结论

本研究构造了一个行车离线后的双炉次场景，其中贪心决策树在存在完整可行映射的情况下仅完成 1 个炉次。Codex 给出的全局重分配多救回 1 个炉次，使准时率由 0.50 提高到 1.00，并通过与决策树相同的硬约束终检。本次演练证明现有分级响应控制器能够在决策树失败后接收并校验 Codex 兜底方案。该结论仅适用于单一合成场景中的接口和约束闭环验证；生产 API 可靠性、模型时延、跨场景泛化能力和真实产线收益仍未得到验证。

## 术语表

| 统一术语 | 定义 | 使用约定 |
| --- | --- | --- |
| 决策树分配器 | 按优先级逐炉次执行的确定性主分配路径 | 不与 LLM 兜底混称。 |
| Codex 兜底 | 当前 Codex 会话在决策树失败后给出的候选映射 | 不称为生产 Codex API 响应。 |
| 分级响应控制器 | 依次执行决策树、满足条件时的 LLM 兜底及 Frozen 处理 | 作为本次验证的系统边界。 |
| 统一硬约束校验器 | 同时校验决策树和 Codex 方案的 `validate_output` | 用于区分“提出方案”和“允许采用”。 |
| Frozen 基线 | 自动恢复不可用时维持原状态并等待人工处理的路径 | 全文统一保留英文 `Frozen`。 |
| 准时率 | 准时完成分配的炉次数除以全部炉次数 | 必须与成功分配数一起报告。 |

| 主张 | 证据 | 状态 |
| --- | --- | --- |
| 构造场景触发了决策树失败。 | 审计路径为 `decision_tree_failure`，仅完成 1/2 个炉次。 | 已支持 |

| 控制器能够调用并校验 Codex 会话方案。 | 审计记录 `controller_called_adapter=true` 且结果为 `llm_react_success`。 | 已支持 |
| Codex 比其他模型或优化器更快、更可靠。 | 未执行外部推理、重复试验或对照实验。 | 缺少证据 |

## 缺失输入与证据边界

- 尚无真实扰动日志用于本次验证。
- 未测量外部 Codex API、模型版本、Token 用量或推理时延。
- 未加入确定性全局优化器作为对照。
- 尚无重复试验、置信区间或失败率估计。
- 报告仅覆盖 `validate_output` 当前已经实现的硬约束，未实现的生产约束不在证据范围内。
