## Context

当前离线扰动基准已经有 20 类场景、AP/AQ/AR 三套结果和位置审计字段，但除行车离线主场景外，其余场景仍以两个固定炉次作为压力夹具。这样会把局部窗口中的其他炉次误显示为上下文，无法回答“该扰动实际影响了哪些炉次”以及“决策树和 Codex 是否对同一批炉次做出了不同决策”。

本变更针对仓库中的离线证据生成链路。输入来自位置感知审计中的真实 PLAN(1)、CRANE 和 `loc_location.xlsx` 映射；事件本身仍是受控注入，用来构造可复现压力场景，不代表历史事故记录。

## Goals / Non-Goals

**Goals:**

- 为目录中的每一个扰动类型，从真实炉次顺序、计划时间、资源分配和位置映射计算局部影响窗口。
- 保留主场景的 31 炉回归结果，并让其他场景的炉次数量由数据计算，而不是由固定的 2、20 或 31 写死。
- 对每个场景建立 AP 基线、AQ 决策树分支和 AR Codex 分支；AQ 与 AR 共享输入快照但互不读取对方结果。
- 让行车、钢包、路线和工艺位置约束进入两条求解线路，并在结果中保存影响范围、状态变化和校验信息。
- 更新基准 JSON/CSV、SQLite 证据和场景图集，使受影响炉次与窗口外上下文可区分。
- 保证离线 Codex 审计字段明确标注 `external_api_called=false`。

**Non-Goals:**

- 不接入生产控制系统、实时 PLC 或外部 LLM API。
- 不根据静态计划分配推断连续的天车物理运动轨迹。
- 不改变决策树的默认生产评分权重，不把 Codex 结果写回 AQ 输入。
- 不把图集改造成新的交互式前端产品，也不调整现有页面的视觉风格。

## Decisions

### 1. 影响窗口采用“事件锚点 + 位置可达性 + 时间邻域”的数据驱动算法

先把完整 PLAN 炉次按源审计中的稳定顺序保留，并使用归一化演示时钟定位扰动发生点。对每个场景，以事件资源对应的真实行车/钢包/工艺位置为中心，筛选在扰动发生后仍可能使用该资源或经过受影响位置的候选炉次，再按计划起始、浇次时间和安全缓冲扩展前后窗口。窗口内已完成或锁定的炉次进入排除集合，窗口外炉次冻结。

算法必须输出候选炉次、最终受影响炉次、锁定排除炉次、窗口边界、使用的定位字段和筛选原因。主场景继续使用已经审计的 11:00 归一化窗口和 31 炉快照，作为兼容性锚点；其他场景复用同一套归一化语义而不是直接复制主场景炉次。

备选方案是对所有场景固定取 20 炉或固定取两个压力炉次。该方案实现简单但不符合真实局部影响范围，且会让图集产生“上下文炉次被当成未求解炉次”的歧义，因此不采用。

### 2. AP 是两条分支的唯一共同基线

每个场景先从位置感知全量审计复制影响窗口内的基线分配，形成 AP。事件状态只作用于场景输入副本；AQ 与 AR 分别接收 AP 副本、同一批炉次、同一批资源和同一位置约束。AR 可以接收 AQ 的失败上下文用于解释，但不得读取或修改 AQ 的分配结果。

这样可以把“共同保持不变的炉次”和“两个分支真正改变的炉次”区分开，也能在评价时准确统计完成率、变更数、约束违反和工厂钢包一致率。

### 3. 统一使用现有校验器和离线 Codex 适配器

场景状态通过现有扰动目录和 `ScenarioValidator` 生成。决策树必须先尝试；当其结果缺炉、资源不可用、路线被阻断或其他硬门槛失败时，才调用保存的 Codex 方案适配器。Codex 方案仍须完整覆盖所有受影响炉次，并通过同一套资源、位置、路线和锁定约束校验。

每个分支保留 assignments、path、验证检查、失败上下文和指标。离线适配器只回放已审计的 Codex 提案，元数据中的 `external_api_called` 固定为 `false`，避免把复现结果误述为线上 API 调用。

### 4. 图集是基准数据的只读投影

图集直接读取 benchmark JSON 的 `heat_results`、AQ/AR assignments 和 `impact_scope`。窗口内炉次按结果着色：AQ/AR 相同、AQ/AR 不同、AQ 失败、AR 补全分别使用已有颜色；窗口外炉次只作为蓝色上下文。图集不得再次运行分配算法，也不得用固定数量补齐影响范围。

对于每个场景，图集同时展示动态受影响炉次数量、AQ/AR 完成状态和主要校验结果。缺少真实取包、落包、作业起止和遥测轨迹时，文案只写计划/调度状态。

### 5. 结果契约和校验顺序

构建顺序固定为：读取源审计和位置映射 → 生成场景窗口 → 生成 AP → 注入事件状态 → AQ 求解 → AR 离线回放 → 两条分支独立验证 → 生成 benchmark/SQLite → 生成图集。构建器在任何场景出现重复炉次、分支集合不一致、位置映射缺失、AP 不是源分配或 AR 改变窗口外炉次时失败。

## Risks / Trade-offs

- [不同扰动的真实物理影响边界没有完整历史事故标签] → 将算法筛选依据、窗口边界、位置映射状态和受控事件状态差异全部写入审计，明确这是可复现压力场景而非事故统计。
- [位置映射存在缺失或同一位置多个编码] → 生成场景前执行映射完整性检查；无法证明位置可达性时保留候选为上下文并在审计中标记，不静默扩大求解窗口。
- [不同场景窗口大小不同，旧图集假设固定行数] → 图集高度和上下文选择均从 benchmark 结果动态生成，并增加不固定炉次数量的回归测试。
- [离线 Codex 提案可能与新窗口不匹配] → 适配器返回前执行完整集合和硬约束校验；提案缺炉、重复或引用窗口外炉次时构建失败。
- [主场景已有独立审计且字段结构略有差异] → 保留主场景审计覆盖逻辑，但在输出前统一成同一 `impact_scope`、`responses` 和 `heat_results` 契约，并用 31 炉回归测试锁定结果。

## Migration Plan

1. 新增数据驱动窗口和位置约束辅助逻辑，保留现有主场景的真实窗口覆盖。
2. 更新离线场景构建器、benchmark 评价器和图集生成器，先在临时输出目录生成 JSON/CSV/HTML。
3. 运行单元测试、OpenSpec 校验和构建脚本，核对 20 类、主场景 31 炉、AQ/AR 集合一致性及 `external_api_called=false`。
4. 通过校验后替换 `outputs/disturbance_solution_benchmark` 和离线 SQLite；若失败，删除新生成的临时输出并保留原审计文件，不修改源 PLAN/CRANE/位置数据。

## Open Questions

- 当前 `loc_location.xlsx` 对部分资源可能只有静态位置映射，没有完整作业轨迹；本变更将其作为可达性和候选筛选依据，不把它扩展成连续运动模型。
- 若后续获得真实事故发生时间和锁定炉次清单，可将其作为场景输入覆盖当前的归一化事件锚点，但不改变 AQ/AR 独立分支契约。
