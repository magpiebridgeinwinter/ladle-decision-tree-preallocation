## Context

仓库已有位置映射后的 457 炉 AP 审计、一个 31 炉行车离线双线路实验，以及覆盖 20 类扰动的离线场景库。当前证据分散在单场景 JSON、SQLite 和 Excel 中：20 类场景没有统一的场景级评分，部分逐行评价把“返回 assign”近似为“校验通过”，也没有明确区分工厂钢包一致率和方案可执行性。

数据边界如下：PLAN、CRANE、loc_location、炉次和资源编号来自真实数据；20 类事故是可复现的受控注入；Codex 结果是已审计的离线候选方案，`external_api_called=false`。PLAN 提供工厂预配钢包，但没有完整的工厂天车分配、人工扰动重排或现场执行结果。

## Goals / Non-Goals

**Goals:**

- 从同一位置映射 AP 基线构建 20 类扰动的可复现实验矩阵。
- 对 AQ 和 AR 使用相同输入、影响范围、资源状态和校验器，保证可比性。
- 用硬门槛先判断方案是否可执行，再比较服务效果和计划稳定性。
- 生成场景、方法和炉次三个粒度的结构化结果，并导出 JSON、CSV 和 Excel。
- 计算可获得的工厂钢包一致率，同时显式记录不可获得的工厂天车和事故后人工方案。

**Non-Goals:**

- 不修改网页、实时 API、原始 PLAN/CRANE/位置文件或现场控制接口。
- 不把受控事故写成真实历史事故，不把离线 Codex 方案写成实时外部 API 调用。
- 不以工厂钢包一致率替代硬约束，不在缺少人工重排记录时宣称优于人工。
- 不训练模型，也不为追求历史一致率修改硬约束。

## Decisions

### 1. 复用离线场景记录作为实验输入

批量实验直接调用 `build_scenario_records`，不从 SQLite 反向拼装业务对象。这样 20 类扰动、受控覆盖项、校验结果和 Codex 审计来自同一个生成入口。SQLite 继续作为持久化与查询副本。

备选方案是直接查询 SQLite。该方案适合展示，但丢失部分构建期对象语义，且容易让实验逻辑依赖数据库布局，因此不采用。

### 2. 独立的基准评价模块

在 `ladle_preallocation/evaluation` 中新增基准评价模块，接收场景记录和可选工厂钢包映射，输出稳定的纯 Python 字典。模块只计算指标和推荐，不写文件；命令行工具负责读取数据并导出结果。

评价数据流为：

```text
位置映射 AP 审计
        ↓
20 类受控扰动记录
        ↓
AQ 决策树 / AR Codex
        ↓
共享校验结果 + 分配明细
        ↓
硬门槛 → 服务指标 → 稳定性指标 → 工厂差异诊断
        ↓
JSON / CSV / Excel
```

### 3. 硬门槛与排序分离

每条线路只有同时满足以下条件才标记为可执行：影响炉次完成率为 100%、所有共享校验通过、锁定/非受影响炉次修改数为 0、未知或不可用资源数为 0。任一门槛失败即不能作为推荐方案。

两条线路都可执行时，按以下顺序比较：按时率、平均延迟、最大延迟、相对 AP 改配炉次数、资源变更数、行车负载离散度。只有前一项相同才比较后一项。工厂钢包一致率单独展示；第一版不把它加入推荐排序，因为历史工厂选择可能包含数据集未记录的隐性规则。

### 4. 工厂结果采用“可比较字段”契约

从 PLAN 的 `preallocated_ladle` 读取有效 `STxx` 钢包编号。每个炉次记录工厂钢包是否存在，以及 AP/AQ/AR 是否与之相同。场景汇总只对存在有效工厂钢包的炉次计算一致率。

工厂天车一致率、人工扰动后方案一致率和现场执行效果固定输出为 `not_available`，并附原因，不能填 0 或推断值。

### 5. 输出一个实验包

输出目录固定为 `outputs/disturbance_solution_benchmark/`：

- `benchmark.json`：完整实验、方法、场景和炉次证据；
- `scenario_comparison.csv`：每场景两条线路的核心指标和推荐；
- `heat_comparison.csv`：逐炉次 AP/AQ/AR、校验、改配及工厂钢包对照；
- `钢包扰动重调度双线路评价.xlsx`：面向审阅者的汇总、场景明细、炉次明细和指标说明。

Excel 只投影 JSON 结果，不在 JavaScript 中重新实现推荐逻辑，避免多份评价规则漂移。

### 6. 证据边界进入数据契约

每个场景保存 `evidence_type`、受控覆盖项、真实来源文件、Codex 调用边界和缺失数据项。总体结论只能声称“在真实数据派生的受控扰动实验中”，不能声称现场生产效果或替代人工。

## Risks / Trade-offs

- [Risk] 20 类场景中除行车离线主场景外，多数只包含两个压力炉次，不能代表全厂事故分布 → 在结果中分别报告 31 炉主场景与双炉压力场景，不把炉次数直接合并为现场成功率。
- [Risk] 离线 Codex 候选方案由固定审计结果生成，无法测量真实模型时延和随机性 → 将求解时长标为建模值，并保留 `external_api_called=false`；实时稳定性另设实验。
- [Risk] 工厂预配钢包缺失或包含人工隐性规则 → 只在有效样本上计算一致率，并将其作为诊断指标。
- [Risk] 原有 Excel 的 AS:AZ 文档与实际 AU:BB 布局不一致 → 新实验工作簿使用独立表结构和字段名，不依赖易变列字母。

## Migration Plan

1. 新增纯评价模块和测试，不修改已有单场景输出。
2. 新增批量构建命令，生成 JSON/CSV，核对 20 类扰动和主场景计数。
3. 使用同一 JSON 生成 Excel，并检查关键范围、公式错误和可读性。
4. 运行完整测试后，将实验包作为新的可审计交付物纳入仓库。

回滚只需删除新增模块、构建工具和输出目录；原有数据及审计不受影响。

## Open Questions

- 工厂人工扰动重排、天车任务和现场执行时间数据尚未提供；获得后可加入第三条“工厂/人工方案”线路。
- 实时 Codex 重复性、P95 时延和 90 秒预算内成功率需要配置 API 后单独验证，不与本次离线实验混合。
